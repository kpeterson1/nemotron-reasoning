# 2026-05-06

## Architecture clarification — Nemotron-H is hybrid Mamba/attention + sparse MoE

While setting up Phase 3 inference I made a mid-thread "correction" claiming the model wasn't really MoE — that was wrong. The actual config shows it is **both** hybrid Mamba/attention **and** Mixture-of-Experts. Logging the full picture here so we don't forget.

### Pulled from `config.json` (cache snapshot)

```
architectures:                       ["NemotronHForCausalLM"]
num_hidden_layers:                   52
hybrid_override_pattern:              MEMEM*EMEMEM*EMEMEM*EMEMEM*EMEMEM*EMEMEMEM*EMEMEMEME
hidden_size:                         2688
num_attention_heads:                 32
num_key_value_heads:                 2          # heavy GQA: 32→2
mamba_num_heads:                     64
mamba_head_dim:                      64
expand:                              2
num_experts_per_tok:                 6
moe_intermediate_size:               1856
moe_shared_expert_intermediate_size: 3712       # DeepSeek-style shared expert
```

### What that pattern decodes to

The 52-character `hybrid_override_pattern` decomposes as:

| symbol | meaning                          | count |
|--------|----------------------------------|------:|
| `M`    | Mamba/SSM layer                  | 23    |
| `E`    | Attention layer (with GQA)       | 23    |
| `*`    | MoE feed-forward layer           | 6     |

So per forward pass, a token sees ~23 Mamba blocks, ~23 GQA-attention blocks, and routes through 6 MoE FFN layers (each picking 6 of N experts plus a shared expert). The "30B total / ~3B active per token" naming is **classic MoE expert routing**, not a Mamba thing.

### Why this matters for our work

1. **KV cache is tiny**: only 2 KV heads × 23 attention layers × dim, plus mamba SSM state (small per-token). With 119 GB unified memory on the GB10, we have an enormous amount of headroom for batching at 4096 ctx — we can probably push `max_num_seqs` well above the default.
2. **LoRA targeting**: the baseline config in `configs/train/lora_baseline.yaml` targets `.*\.(in_proj|out_proj|up_proj|down_proj)$` which catches mamba projections (`in_proj`/`out_proj`) AND attention projections (`up_proj`/`down_proj` via the FFN naming). Whether it touches the MoE expert weights depends on how the experts are named — to verify after first training run.
3. **Inference cost is dominated by routing + memory bandwidth**, not FLOPs at the active-param level. Mamba layers add a constant per-token cost regardless of context, so long contexts are cheap.
4. **Active params depend on shared expert**: `num_experts_per_tok=6` selects 6 routed experts, but there's also a shared expert (`moe_shared_expert_intermediate_size=3712`) that runs every token. So per-token compute is `6 * moe_intermediate_size + moe_shared_expert_intermediate_size = 6*1856 + 3712 = 14848` for the MoE FFN, on top of attention/mamba.

### Decisions

- README.md will say "hybrid Mamba/attention + sparse MoE FFN" not just "MoE".
- After first generation we'll verify token throughput on the GB10 — long-context speed is the biggest unknown given the hybrid layers.
- LoRA target pattern needs a verification check (Phase 5) — print the named modules touched after `get_peft_model` to confirm coverage of MoE experts vs only mamba/attention projections.
